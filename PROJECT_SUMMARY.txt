1. PROJECT OVERVIEW & CORE OBJECTIVES
================================================================================
Traditional real estate and land record systems suffer from critical vulnerabilities,
including:
- Forged property titles and duplicate sales of the same land parcel.
- Paper-based deed tampering and human manipulation.
- Lengthy, opaque verification procedures involving unauthorized middlemen.
- Lack of fractional real estate investment opportunities for retail buyers.

This project delivers a custom, cryptographically secure Blockchain in Python
tailored specifically to address these issues.

Key Objectives Achieved:
1. Tamper-Proof Land Title Registry using SHA-256 cryptographic chaining.
2. 3-Layer Ownership Verification:
   - Layer 1: Document Integrity Hashing (IPFS CID generation).
   - Layer 2: Simulated Government Authority Verification (ECDSA signature).
   - Layer 3: Blockchain Immutability and Proof-of-Work Consensus.
3. Real Estate Tokenization for fractional ownership (e.g., 100 equity shares).
4. Automated Rental Yield / Dividend Distribution across fractional token holders.
5. Instant Tamper Detection via Binary Merkle Trees and block header hashes.
6. Password-Protected Keystore storing user credentials encrypted with AES-256.
7. Full Ledger and Keystore Persistence to local disk storage.

================================================================================
2. SYSTEM ARCHITECTURE & 3-LAYER VERIFICATION MODEL
================================================================================
The project strictly enforces a 3-Layer Verification Architecture:

+------------------------------------------------------------------------------+
|                   LAYER 1: DOCUMENT INTEGRITY VERIFICATION                   |
|  - Land deed, surveyor map, and GIS coordinates are hashed.                  |
|  - Produces a deterministic IPFS Content Identifier (CID prefix 'Qm...').    |
|  - Bound immutably to the property registration transaction.                 |
+------------------------------------------------------------------------------+
                                       |
                                       v
+------------------------------------------------------------------------------+
|                 LAYER 2: SIMULATED AUTHORITY VERIFICATION                    |
|  - Government Land Registrar reviews deed, coordinates, and title history.   |
|  - Layer 1 document hash is re-computed and matched against the submission.  |
|  - Registrar cryptographically signs an approval transaction using ECDSA.    |
|  - Unverified properties CANNOT be transferred or tokenized.                 |
+------------------------------------------------------------------------------+
                                       |
                                       v
+------------------------------------------------------------------------------+
|                LAYER 3: BLOCKCHAIN IMMUTABILITY & CONSENSUS                  |
|  - Transactions are structured into binary Merkle Trees.                     |
|  - Mined into blocks via Proof-of-Work (PoW) consensus.                     |
|  - Prevents double-selling, retroactive alteration, or unauthorized transfer. |
+------------------------------------------------------------------------------+

3. CHRONOLOGICAL DEVELOPMENT PROCESS (ALL PHASES COMPLETED)
================================================================================

PHASE 1: ENVIRONMENT SETUP & DEPENDENCY CONFIGURATION
------------------------------------------------------
- Verified Python environment (Python 3.14 on Windows 64-bit).
- Created 'requirements.txt' specifying necessary cryptographic and styling libraries:
  * cryptography >= 41.0.0 (SECP256K1 elliptic curves, PKCS#8, AES-256)
  * rich >= 13.0.0 (Terminal formatting, tables, panels)

PHASE 2: CRYPTOGRAPHIC WALLET & IDENTITY GENERATION
----------------------------------------------------
- Developed 'blockchain/wallet.py':
  * Generates asymmetric key pairs using ECDSA on the SECP256K1 curve (same standard
    used by Bitcoin and Ethereum).
  * Derives unique public addresses in Ethereum format (0x + first 40 hex chars).
  * Generates and verifies DER-encoded digital signatures for transaction integrity.
  * Supports PEM serialization and password-protected key export/import.

PHASE 3: MERKLE TREE TRANSACTION ENGINE
---------------------------------------
- Developed 'blockchain/merkle.py':
  * Implements binary Merkle Trees over transaction hashes.
  * Computes the 64-character SHA-256 Merkle Root stored inside block headers.
  * Generates cryptographic inclusion proofs and verifies transaction membership.

PHASE 4: DOMAIN TRANSACTION MODELS & DIGITAL SIGNING
----------------------------------------------------
- Developed 'blockchain/transaction.py':
  * REGISTER_PROPERTY: Encapsulates property ID, cadastral survey number, GIS
    location, area (sq ft), market value, IPFS document hash, and owner details.
  * VERIFY_PROPERTY: Encapsulates registrar approval, Layer 1 & 2 pass flags.
  * TRANSFER_OWNERSHIP: Encapsulates deed handover between buyer and seller.
  * TOKENIZE_PROPERTY: Splits full property equity into fractional shares.
  * TRANSFER_TOKENS: Transfers fractional shares between retail investors.
  * DISTRIBUTE_RENT: Disburses rental dividends proportionally to token holders.
  * Enforces signature generation and signature validation on every transaction.

PHASE 5: BLOCK STRUCTURE & PROOF-OF-WORK CONSENSUS
--------------------------------------------------
- Developed 'blockchain/block.py':
  * Defines block header: index, timestamp, previous_hash, merkle_root, nonce, hash.
  * Computes block hash using SHA-256 over canonical header JSON.
  * Implements Proof-of-Work mining loop targeting difficulty (leading zeros).
  * Re-calculates Merkle root dynamically from transaction contents.

PHASE 6: BLOCKCHAIN CORE, MEMPOOL & STATE MACHINE
-------------------------------------------------
- Developed 'blockchain/blockchain.py':
  * Genesis Block (Block #0) creation.
  * Transaction mempool for pending transactions.
  * State Machine ('RegistryState') tracking active properties, token balances,
    ownership titles, and authorized registrar accounts.
  * Cryptographic Chain Audit ('is_chain_valid'): Verifies block hashes, previous
    hash links, PoW difficulty, Merkle roots, and transaction signatures.
  * Ledger persistence: 'save_to_file' and 'load_from_file' to JSON.

PHASE 7: MULTI-LAYER VERIFICATION ORCHESTRATOR
----------------------------------------------
- Developed 'blockchain/land_registry.py':
  * High-level coordinator linking wallets, documents, registrar, and ledger.
  * Simulates IPFS document upload and hashing.
  * Enforces business rules: properties must be registered, pass Layer-1 doc check,
    and receive Layer-2 registrar digital signatures before trading or tokenization.

PHASE 8: INTERACTIVE CLI DEMONSTRATION
--------------------------------------
- Developed 'demo.py':
  * Cross-platform (Windows CP1252 / UTF-8 safe) visual demonstration.
  * Simulates 6 roles: Registrar, Alice (Owner), Bob (Buyer), Charlie & Diana
    (Fractional Investors), and Miner Node.
  * Executes all 11 phases end-to-end including simulated hacker tamper attacks.

PHASE 9: PASSWORD-PROTECTED KEYSTORE & KEY PERSISTENCE
-----------------------------------------------------
- Developed 'blockchain/keystore.py':
  * Allows users to store private keys safely in the 'wallets/' folder.
  * Uses AES-256-CBC via PKCS#8 password encryption.
  * Enables reading public profiles (address, public key) without a password.
  * Requires user password to decrypt private key for transaction signing.

PHASE 10: AUTOMATED TEST SUITE IMPLEMENTATION
---------------------------------------------
- Developed 'tests/test_blockchain.py' (6 tests) and 'tests/test_keystore.py' (5 tests).
- Achieved 100% test pass rate (11/11 tests passing in 0.19s).

5. KEY STORAGE ARCHITECTURE: PUBLIC KEY VS. USER PRIVATE KEY
================================================================================

1. USER KEY (PRIVATE KEY):
   - Storage Location : Local client keystore folder ('wallets/<label>.json').
   - Encryption       : AES-256-CBC via PKCS#8 with user-chosen passphrase.
   - Access Control   : Strictly private to the user. Never transmitted over the
                        network, never written to the blockchain, never stored
                        in plaintext.
   - Purpose          : Signs registration requests, approvals, deed transfers,
                        and token transactions.

2. PUBLIC KEY:
   - Storage Location : Published ON-CHAIN inside every transaction payload
                        ('sender_public_key_pem') and stored in block records.
   - Access Control   : Publicly inspectable by any participant or auditor.
   - Purpose          : Allows any peer node to mathematically verify transaction
                        signatures without relying on a central authority.

3. WALLET ADDRESS (0x...):
   - Storage Location : Ledger state machine ('owner_address', 'token_holders')
                        and database user profiles.
   - Derivation       : 0x + first 40 hex characters of SHA-256(public_key_bytes).
   - Purpose          : Serves as the public identifier for land and token ownership.
